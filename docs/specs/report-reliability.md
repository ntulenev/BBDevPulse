# Надёжность анализа Bitbucket и согласованность отчётов

**Статус** — реализовано и проверено автоматическими тестами.
**Область** — сбор данных Bitbucket, дисковый кэш анализа PR, параллельная обработка и вывод в консоль, HTML и PDF. Файлы `appsettings*` за рамками работ.

Код уже содержал основную реализацию всех пяти разделов на момент проверки. Дополнительно устранено досрочное завершение чтения коммитов: полнота теперь устанавливается только после успешного обхода всех страниц. Отмена, совпавшая с ошибкой вспомогательного запроса, прерывает анализ. Детальные разделы разработчиков во всех форматах используют выбранный режим размера PR и явно отмечают недоступные значения. Проверка: `dotnet test BBDevPulse.slnx` — 558 тестов успешно.

## 1. Отличать нулевые показатели от недоступных данных

До реализации методы получения коммитов и размеров в `PullRequestAnalyzer` могли преобразовать ошибку API в пустой результат. Такой снимок получал `HasEnrichment = true` и при повторном запуске считался полным.

- Для списка коммитов, размера PR и запрашиваемых размеров коммитов различать успешный ответ (включая пустой) и ошибку получения. Пагинируемая выборка считается полной после успешной загрузки последней страницы.
- При исчерпании повторов для вспомогательного запроса сохранить доступные показатели. Во всех форматах обозначить недоступную метрику и исключить её из агрегатов. Успешный ноль включать в выборку. Если выборка пуста, вывести «нет данных».
- Сохранять полноту по компонентам. При том же ключе снимка повторно запросить недостающие компоненты, после успеха обновить снимок. Сменить версию формата кэша, чтобы старые ложные нули не переиспользовались. Отмену передавать вызывающему коду.

**Приёмка.** На первом запуске запрос размера PR исчерпывает попытки, остальные данные доступны. Во всех трёх отчётах размер помечен как недоступный. При втором запуске тот же PR получает корректный размер, при третьем он читается из кэша. Отдельные тесты покрывают успешный нулевой diff, сбой второй страницы коммитов и чтение старого снимка.

## 2. Проверять адреса страниц до отправки запроса

`BitbucketClient` принимает относительные и абсолютные ссылки из поля `next`. `PaginatorHelper` следует по ним до конца последовательности. Транспорт использует клиент с заголовком авторизации по умолчанию.

- Разрешить ссылку в итоговый URI по тем же правилам, что и при отправке запроса. Проверить совпадение схемы, хоста и эффективного порта с базовым адресом API. Отклонить некорректную ссылку до обращения к HTTP-транспорту.
- В рамках каждого перечисления отслеживать посещённые URI с учётом query-параметров курсора. Повтор страницы завершает перечисление с диагностикой. Не выводить учётные данные в сообщении об ошибке.

**Приёмка.** Относительная и абсолютная ссылки на следующую страницу API работают. Подмена хоста, порта или схемы, включая ссылку вида `//other.example/path`, отклоняется. Тестовый HTTP-обработчик не получает запроса на чужой адрес. В цикле A → B → A третьего запроса нет.

## 3. Корректно завершать параллельную работу

До реализации в `PullRequestAnalyzer` ожидание запущенных задач следовало за перечислением PR. Ошибка чтения следующей страницы могла привести к освобождению семафора до завершения обработчиков. Аналогичный порядок использовался на уровне репозиториев в `SpectreRepositoryAnalysisPresenter`.

- На обоих уровнях сохранить действующие лимиты параллелизма. При ошибке источника или отмене прекратить выдачу новой работы, сигнализировать активным обработчикам и дождаться их завершения до освобождения ресурсов.
- Сохранить исходную причину сбоя. После возврата метода обработчики больше не меняют отчёт и индикатор прогресса.
- В `Program` связать Ctrl+C с токеном всего запуска. При прерванном сборе завершить команду без публикации итогового отчёта об успешном анализе.

**Приёмка.** Управляемый тест удерживает обработку первого PR и имитирует ошибку второй страницы. Метод завершается после остановки обработчика и возвращает исходную ошибку. Второй тест отменяет обработку, пока очередной репозиторий ждёт свободного слота. В обоих случаях счётчик активных обработчиков в конце равен нулю.

## 4. Учитывать ответ сервера при повторных GET-запросах

До реализации в `BitbucketTransport` повтор был предусмотрен для 429, а `RetryPolicyHelper` рассчитывал общую паузу по локальной формуле.

- Для 429 и временных 502, 503, 504 повторять GET в пределах существующего бюджета попыток. Для 401 и 403 сразу вернуть ошибку. Сохранить HTTP-статус при исчерпании бюджета.
- Поддержать обе формы `Retry-After` — число секунд и HTTP-дату. Действительную будущую границу учитывать в общей паузе для запросов клиента. При отсутствующем, просроченном или некорректном значении применять существующую задержку. Если ожидание превышает допустимый максимум, завершить запрос с диагностикой без досрочного повтора.
- Отмена прерывает ожидание. Проверять расчёт задержек с управляемым временем.

**Приёмка.** Последовательности 429 → 200 и 503 → 200 успешно завершаются. Параллельный запрос соблюдает уже установленную паузу. Отдельно проверить HTTP-дату, некорректный заголовок, исчерпание бюджета, отсутствие повторов для 401/403 и отмену во время ожидания.

## 5. Унифицировать подготовку статистики

Начать со времени до первого ревью (TTFR). До реализации выборки и сводные значения готовились в представлениях. Общий расчёт должен определять состав выборки и численные значения для всех трёх форматов.

- Зафиксировать действующие правила отбора наблюдений тестом. Подготовить число наблюдений, медиану и P75 один раз, используя существующий `StatisticsCalculator`. PR без первого ревью исключать из выборки.
- Передавать результат в `SpectreStatisticsPresenter`, `HtmlContentComposer` и `QuestPdfReportRenderer`. Округление для отображения, подписи и вёрстку оставить формату вывода.

**Приёмка.** Для длительностей 0, 2 и 4 рабочих часа и одного PR без ревью выборка содержит три наблюдения, медиана равна 2 часам, P75 — 3 часам. Все три представления используют эти значения. Отдельно проверить выборку без наблюдений.

## Порядок поставки и проверка

Каждый раздел реализуется отдельным изменением в указанном порядке. Первые два независимы. Общую агрегацию внедрять после определения семантики недоступных значений. Для каждого изменения добавить регрессионные сценарии в соответствующую группу `BBDevPulse.Tests` и выполнить `dotnet test BBDevPulse.slnx`. Для сетевых сценариев использовать тестовый HTTP-обработчик, для повторных запусков — временный каталог кэша.
